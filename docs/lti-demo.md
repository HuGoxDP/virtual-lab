# LTI demo stand (Moodle 5.0 + virtual-lab, offline, HTTPS)

A reproducible local stand for demonstrating virtual-lab as an LTI 1.3 tool inside Moodle. It lives
in `virtual-lab/lti-demo/` and is separate from the production `docker-compose.yml` (own compose
project `lti-demo`, own volumes, own databases). Nothing is exposed beyond the host's ports 80/443.

LTI 1.3 launches are cross-site form POSTs, so both sites run over HTTPS (cookies must be
`SameSite=None; Secure`). A local CA signs one certificate that covers both host names.

| What | URL | Notes |
|---|---|---|
| Moodle | `https://moodle.lti.test` | Moodle 5.0.2 (Bitnami legacy image) + MariaDB 11.4 |
| Platform (virtual-lab) | `https://lab.lti.test` | built from this repo (`../backend`, `../Dockerfile.frontend`) |

(The names are fixed in `lti-demo/docker-compose.yml`, `proxy/nginx.conf`, `proxy/gen-certs.sh`; if they
change, change them in those three places and here.)

## One-time manual steps on the host (Windows)

The stand does not touch Windows settings. Do these once:

1. **Hosts file** (Administrator PowerShell) so the browser resolves the names:
   ```powershell
   Add-Content C:\Windows\System32\drivers\etc\hosts "127.0.0.1 moodle.lti.test lab.lti.test"
   ```
2. **Trust the local CA** so the browser shows no certificate warning. After the first `up` the CA is at
   `virtual-lab/lti-demo/certs/ca.crt`. Import it into *Trusted Root Certification Authorities*:
   ```powershell
   Import-Certificate -FilePath .\certs\ca.crt -CertStoreLocation Cert:\CurrentUser\Root
   ```
   (CurrentUser store: no admin rights needed, Windows shows one confirmation dialog.) Chrome and Edge use the
   Windows store; Firefox needs the same file under Settings > Certificates > Authorities, or
   `security.enterprise_roots.enabled = true`. Restart the browser afterwards. To undo, delete the
   "WebEngine LTI demo local CA" certificate from the same store.

Inside Docker nothing manual is needed: the proxy container carries the aliases `moodle.lti.test` and
`lab.lti.test` on the `lti-demo` network, so Moodle reaches `https://lab.lti.test` and the platform backend
reaches `https://moodle.lti.test` through the same TLS endpoint a browser uses. Moodle trusts the CA through
`curl.cainfo` (`moodle/php-ca.ini`), the backend through `NODE_EXTRA_CA_CERTS`.

## Up / down

```bash
cd virtual-lab/lti-demo
docker compose up -d --build     # first run 5-10 min: image pulls, Angular build, Moodle install (~3 min)
docker compose ps                # wait until moodle is "healthy"
docker compose logs -f moodle    # "Moodle setup finished" + "seed done"
docker compose down              # stop, keep data
docker compose down -v           # wipe everything (Moodle and platform data, certs stay in ./certs)
```

`./certs` is generated by the `certs` service on first `up` and kept across `down -v` (so the CA you
trusted stays valid). Delete the folder to regenerate (then re-import the CA).

Port 80/443 busy? Set `LTI_HTTPS_PORT` / `LTI_HTTP_PORT` in `.env` (URLs then need the port, and Moodle's
`wwwroot` must be changed too, so prefer freeing 443).

## Check without a browser

```bash
cd virtual-lab/lti-demo
# --ssl-no-revoke only for the Windows curl (schannel), which cannot reach a CRL for a private CA
R="--resolve moodle.lti.test:443:127.0.0.1 --resolve lab.lti.test:443:127.0.0.1 --cacert certs/ca.crt --ssl-no-revoke"
curl $R -sS -o /dev/null -w '%{http_code}\n' https://moodle.lti.test/login/index.php   # 200
curl $R -sS https://lab.lti.test/api/health            # {"status":"ok","db":"connected",...}
curl $R -sS https://lab.lti.test/api/catalog           # 200; the fresh database holds no scenarios yet
# server-to-server, from inside the containers (neither image has curl):
docker compose exec moodle php -r '$c=curl_init("https://lab.lti.test/api/health");curl_setopt($c,CURLOPT_RETURNTRANSFER,1);echo curl_exec($c),curl_getinfo($c,CURLINFO_HTTP_CODE);'
docker compose exec platform-api node -e 'fetch("https://moodle.lti.test/login/index.php").then(r=>console.log(r.status))'
# course and accounts
docker compose exec moodle-db mariadb -ubn_moodle -plti-demo-moodle-db bitnami_moodle -e "select shortname from mdl_course; select username from mdl_user"
```
## Where things are in Moodle

- **Manage tools** (LTI tool registration): Site administration > Plugins > Activity modules > External tool >
  Manage tools, i.e. `https://moodle.lti.test/mod/lti/toolconfigure.php` (log in as `admin`).
- Course: `https://moodle.lti.test/course/view.php?name=LAB101`.
- Moodle's block on private addresses (`curlsecurityblockedhosts`) is cleared by `moodle/seed.php`, because every
  container address is private. Demo only.

## Known limits / later phases

- The platform's nginx sends `X-Frame-Options: SAMEORIGIN` and `frame-ancestors`-style CSP; embedding the
  platform inside a Moodle iframe (deep-link picker, in-course launch) needs those relaxed on the LTI routes. That is
  the LTI code phases' job, not this stand's.
- Full walkthrough (register tool, pick a lab, launch as a student, grade in the gradebook) is Phase 7.
- Stand secrets are demo defaults on purpose; never reuse them anywhere reachable.
- Moodle runs with `sslproxy` only. `reverseproxy` must stay off: the site is reached under the same host name
  inside and outside the proxy, and Moodle answers 500 "Reverse proxy enabled so the server cannot be accessed
  directly" in that case.
- Observed for Phase 7: Moodle's `MoodleSession` cookie is `Secure; HttpOnly` with **no SameSite attribute**
  (browsers treat that as Lax). The platform's own cookies, if LTI adds any, must set `SameSite=None; Secure`.
- The catalog of a fresh stand is empty; publish a scenario through `/admin` (token above) or
  `backend` `npm run publish:release` pointed at the stand before demonstrating a launch.
- Moodle's init script (`moodle/seed.php`) runs once per Moodle volume (Bitnami marker); to re-run it:
  `docker compose exec moodle php /docker-entrypoint-init.d/10-seed.php`.

## LTI registration and launch (Phase 4 backend)

The platform backend is an LTI 1.3 tool (`backend/lti/`, mounted at `/api/lti`; env in `.env.example`). The stand sets
`LTI_PUBLIC_URL=https://lab.lti.test`, `LTI_REGISTRATION_SECRET` (default `lti-demo-registration-secret`, override with
`LTI_REGISTRATION_SECRET` in `lti-demo/.env`) and keeps the tool's RSA key on the `lti_platform_lti` volume.

| Endpoint | Purpose |
|---|---|
| `GET /api/lti/jwks` | the tool's public key |
| `GET /api/lti/register?secret=...` | Dynamic Registration (Moodle appends `openid_configuration` and `registration_token`) |
| `GET\|POST /api/lti/login` | OIDC initiation |
| `POST /api/lti/launch` | `id_token` validation, session cookie `lti_session`, redirect to `/play/:id?lti=1` or `/lti/pick` |

After changing backend code or nginx, rebuild only the platform: `docker compose up -d --build platform-api platform-web`,
then `docker compose restart proxy` (the proxy caches the old container address of `platform-web`).

### Register the tool in Moodle (browser, the normal way)

1. Log in as `admin`, open Manage tools (`https://moodle.lti.test/mod/lti/toolconfigure.php`).
2. In *Tool URL or registration URL* paste
   `https://lab.lti.test/api/lti/register?secret=lti-demo-registration-secret` and press *Add LTI Advantage*.
3. The window shows "Інструмент зареєстровано" and closes itself. The tool appears as *Pending*: press *Activate*.
4. In course LAB101 add an *External tool* activity, choose the tool, and put `scenario_id=circuits` into
   *Custom parameters* (Phase 5's deep link will set this for the teacher).

### Smoke without a browser (what was run for DW-4.4, 2026-10-28)

All requests from the host with `R="--resolve moodle.lti.test:443:127.0.0.1 --resolve lab.lti.test:443:127.0.0.1 --cacert certs/ca.crt --ssl-no-revoke"`
and cookie jars; Moodle's login form needs its `logintoken` first.

```text
1. admin login (POST /login/index.php with logintoken)                      -> 303, MoodleSession cookie
2. GET /mod/lti/startltiadvregistration.php?url=<register URL>&sesskey=...    -> 302 to <register URL>&openid_configuration=...&registration_token=...
3. GET that Location                                                         -> 200 "Інструмент зареєстровано"
   platform log: [LTI] registered platform https://moodle.lti.test as client FHPGYDKOYPWeRVW
   platform db:  lti_registrations = (https://moodle.lti.test, FHPGYDKOYPWeRVW, {1}, .../mod/lti/auth.php, .../token.php, .../certs.php)
4. activate the tool + create the activity (no plain link exists: the tool list is rendered by JS):
   docker compose cp activity.php moodle:/tmp/ && docker compose exec moodle php /tmp/activity.php
   (sets mdl_lti_types.state = LTI_TOOL_STATE_CONFIGURED, adds "Circuits smoke" to LAB101 -> cmid=2)
5. student login, GET /mod/lti/launch.php?id=2                                -> 200, auto-submit form to https://lab.lti.test/api/lti/login
6. POST that form to /api/lti/login                                          -> 302 to https://moodle.lti.test/mod/lti/auth.php?...state&nonce..., Set-Cookie lti_state_<state>
7. GET the Location with the student's Moodle cookie                          -> 200, auto-submit form with id_token + state
8. POST id_token + state + the lti_state cookie to /api/lti/launch            -> 303 Location: /play/circuits?lti=1
   Set-Cookie: lti_session=...; Path=/; Max-Age=14400; HttpOnly; Secure; SameSite=None
   lti_sessions row: sub=4 role=learner context_id=2 resource_link_id=1 scenario_id=circuits message_type=resource
                     lineitem_url=https://moodle.lti.test/mod/lti/services.php/2/lineitems/2/lineitem?type_id=1
9. POST the same body again                                                  -> 403 (state already used)
```

Not exercised on the stand (covered by the fake-Moodle tests): the teacher's deep-linking launch, which needs Phase 6's
`/lti/pick` page to be useful; `/play/circuits?lti=1` itself is Phase 6.

Nginx note: `location ^~ /api/lti/` in `nginx/nginx.conf` sends no `X-Frame-Options` and no platform CSP; the LTI router sets
its own (`default-src 'none'`; the registration page adds a nonce and the platform's origin as `frame-ancestors`).
`LTI_REGISTRATION_SECRET` must be at least 16 characters, otherwise registration answers 503. The registration secret sits in a URL: it lands in nginx access logs and browser history, so rotate it after registering.

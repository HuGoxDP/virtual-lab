# LTI demo stand (Moodle 5.0 + virtual-lab, offline, HTTPS)

A reproducible local stand for demonstrating virtual-lab as an LTI 1.3 tool inside Moodle. It lives
in `virtual-lab/lti-demo/` and is separate from the production `docker-compose.yml` (own compose
project `lti-demo`, own volumes, own databases). Nothing is exposed beyond the host's ports 80/443.

LTI 1.3 launches are cross-site form POSTs, so both sites run over HTTPS (cookies must be
`SameSite=None; Secure`). A local CA signs one certificate that covers both host names.

| What | URL | Notes |
|---|---|---|
| Moodle | `https://moodle.lti.test` | Moodle 5.0.2 (Bitnami legacy image) + MariaDB 11.4 |
| Platform (virtual-lab) | `https://lab.lti.test` | built from this repo (`../backend`, `../Dockerfile.frontend`) |

(The names are fixed in `lti-demo/docker-compose.yml`, `proxy/nginx.conf`, `proxy/gen-certs.sh`; if they
change, change them in those three places and here.)

## One-time manual steps on the host (Windows)

The stand does not touch Windows settings. Do these once:

1. **Hosts file** (Administrator PowerShell) so the browser resolves the names:
   ```powershell
   Add-Content C:\Windows\System32\drivers\etc\hosts "127.0.0.1 moodle.lti.test lab.lti.test"
   ```
2. **Trust the local CA** so the browser shows no certificate warning. After the first `up` the CA is at
   `virtual-lab/lti-demo/certs/ca.crt`. Import it into *Trusted Root Certification Authorities*:
   ```powershell
   Import-Certificate -FilePath .\certs\ca.crt -CertStoreLocation Cert:\CurrentUser\Root
   ```
   (CurrentUser store: no admin rights needed, Windows shows one confirmation dialog.) Chrome and Edge use the
   Windows store; Firefox needs the same file under Settings > Certificates > Authorities, or
   `security.enterprise_roots.enabled = true`. Restart the browser afterwards. To undo, delete the
   "WebEngine LTI demo local CA" certificate from the same store.

Inside Docker nothing manual is needed: the proxy container carries the aliases `moodle.lti.test` and
`lab.lti.test` on the `lti-demo` network, so Moodle reaches `https://lab.lti.test` and the platform backend
reaches `https://moodle.lti.test` through the same TLS endpoint a browser uses. Moodle trusts the CA through
`curl.cainfo` (`moodle/php-ca.ini`), the backend through `NODE_EXTRA_CA_CERTS`.

## Up / down

```bash
cd virtual-lab/lti-demo
docker compose up -d --build     # first run 5-10 min: image pulls, Angular build, Moodle install (~3 min)
docker compose ps                # wait until moodle is "healthy"
docker compose logs -f moodle    # "Moodle setup finished" + "seed done"
docker compose down              # stop, keep data
docker compose down -v           # wipe everything (Moodle and platform data, certs stay in ./certs)
```

`./certs` is generated by the `certs` service on first `up` and kept across `down -v` (so the CA you
trusted stays valid). Delete the folder to regenerate (then re-import the CA).

Port 80/443 busy? Set `LTI_HTTPS_PORT` / `LTI_HTTP_PORT` in `.env` (URLs then need the port, and Moodle's
`wwwroot` must be changed too, so prefer freeing 443).

## Reset before a demo (one command)

```powershell
cd virtual-lab\lti-demo
.\reset-demo.ps1        # idempotent; never runs `down -v`; Windows PowerShell 5.1 or pwsh 7
```

What it does, in order: waits for the containers to be healthy; reruns `moodle/seed.php` (course, `teacher`/`student`/`student2`,
enrolments); runs `moodle/reset.php` as the web user (deletes every `lti` activity of LAB101, which removes its gradebook
items and grades; asserts the tool is Active, "Show in activity chooser" and default launch container "New window", fixing
them if not); creates or updates the two scenarios of `demo-catalog.json` (`electric-circuits`, graded, from
`ScenarioCreator/ReleaseScenarios/Circuits.zip`; `molecules`, from `Molecules.zip`), publishes them, uploads the archives
through `POST /api/scenarios/:id/archive` and repairs the category labels (the API keeps a stored label, so this one step is
SQL, with the text passed as hex of its UTF-8 bytes); purges `lti_sessions` / `lti_states` (registrations and the tool key
stay); checks `GET /api/catalog`. It reaches the platform with `curl.exe --resolve` and the stand CA, so it needs neither the
hosts entry nor the trusted CA. Other catalog rows are reported, never deleted. Use `-ReleaseDir <folder>` if the
ScenarioCreator checkout is elsewhere. Not scriptable: the tool *registration* itself (a missing one stops the script with
a pointer to "Register the tool in Moodle" below) and the one-time hosts/CA steps. The demo script and the values that solve the
Circuits tasks: [`lti-demo-cheatsheet.md`](lti-demo-cheatsheet.md).

## Known limits / later phases

- The platform's nginx sends `X-Frame-Options: SAMEORIGIN` and `frame-ancestors 'self'` on every page except one:
  `/lti/pick` (the Deep Linking picker, which Moodle 5 shows in a modal iframe) is served with
  `frame-ancestors <LTI_FRAME_ANCESTORS>` and no `X-Frame-Options`. The stand sets `LTI_FRAME_ANCESTORS=https://moodle.lti.test`
  on `platform-web`. The in-course *launch* is not framed: the tool's default launch container is "New window".
- The full walkthrough (register tool, pick a lab, launch as a student, grade in the gradebook) is recorded in
  "Full walkthrough" at the end of this file, including the teacher's pick inside Moodle's own modal.
- Stand secrets are demo defaults on purpose; never reuse them anywhere reachable.
- Moodle runs with `sslproxy` only. `reverseproxy` must stay off: the site is reached under the same host name
  inside and outside the proxy, and Moodle answers 500 "Reverse proxy enabled so the server cannot be accessed
  directly" in that case.
- Observed for Phase 7: Moodle's `MoodleSession` cookie is `Secure; HttpOnly` with **no SameSite attribute**
  (browsers treat that as Lax). The platform's own cookies (`lti_session`, `lti_state_*`) are
  `SameSite=None; Secure; HttpOnly; Partitioned`: the last one keeps them working in the "Select content" iframe, where
  they are third-party cookies.
- The catalog of a fresh stand is empty; publish a scenario through `/admin` (token above) or
  `backend` `npm run publish:release` pointed at the stand before demonstrating a launch.
- Moodle's init script (`moodle/seed.php`) runs once per Moodle volume (Bitnami marker); to re-run it:
  `docker compose exec moodle php /docker-entrypoint-init.d/10-seed.php`.

## LTI registration and launch (Phase 4 backend)

The platform backend is an LTI 1.3 tool (`backend/lti/`, mounted at `/api/lti`; env in `.env.example`). The stand sets
`LTI_PUBLIC_URL=https://lab.lti.test`, `LTI_REGISTRATION_SECRET` (default `lti-demo-registration-secret`, override with
`LTI_REGISTRATION_SECRET` in `lti-demo/.env`) and keeps the tool's RSA key on the `lti_platform_lti` volume. `platform-web` gets `LTI_FRAME_ANCESTORS=https://moodle.lti.test`
(which origins may frame `/lti/pick`; see `.env.example`).

| Endpoint | Purpose |
|---|---|
| `GET /api/lti/jwks` | the tool's public key |
| `GET /api/lti/register?secret=...` | Dynamic Registration (Moodle appends `openid_configuration` and `registration_token`) |
| `GET\|POST /api/lti/login` | OIDC initiation |
| `POST /api/lti/launch` | `id_token` validation, session cookie `lti_session`, redirect to `/play/:id?lti=1` or `/lti/pick` |
| `GET /api/lti/session` | `{ scenarioId, role, messageType, graded, submitted: { score } \| null }`; `submitted` is asked of Moodle (AGS Results), remembered in memory for 30 s per learner and line item; `null` also when that lookup fails for any reason (Moodle down, tool key unreadable) |
| `POST /api/lti/submit` | JSON `{ score? }` (0..1): the learner's score to the Moodle gradebook, once (Phase 5) |
| `POST /api/lti/deep-link` | JSON or form `{ scenarioId }`: the teacher's pick, answered as an auto-submit page to Moodle (Phase 5) |

Hardening notes (no API shape changed):

- **`iat` window.** A launch `id_token` is accepted only when its `iat` is at most 60 s in the future and at most 10 min
  old (the login state's lifetime), besides the usual `exp` check; otherwise 401.
- **Client address for the rate limit.** `TRUST_PROXY` (default `1`, the production nginx) says how many proxies sit
  before the API, so `X-Forwarded-For` yields the real client and each user has their own `/api/lti` bucket. The stand
  sets `2` (TLS proxy + nginx); `0` means no proxy and the header is ignored. `true`/`all` are refused. See `.env.example`.
- **Moodle calls are cached in memory** (per process, bounded): the AGS access token per registration until a minute before
  its `expires_in`, and the "already submitted?" answer per learner and line item for 30 s. A successful submit or a 409
  drops that answer. `POST /submit` always re-reads the Result from Moodle; only the token may be reused.
- **Degradation.** If the grade lookup fails for a reason that is not Moodle's (e.g. the tool key cannot be loaded),
  `GET /session` still answers with `submitted: null`; `POST /submit` answers `503 { error }` instead of a bare 500.

After changing backend code or nginx, rebuild only the platform: `docker compose up -d --build platform-api platform-web`,
then `docker compose restart proxy` (the proxy caches the old container address of `platform-web`).

Nginx note: `location ^~ /api/lti/` in `nginx/nginx.conf` sends no `X-Frame-Options` and no platform CSP; the LTI router sets
its own (`default-src 'none'`; the registration page adds a nonce and the platform's origin as `frame-ancestors`).
`LTI_REGISTRATION_SECRET` must be at least 16 characters, otherwise registration answers 503. The registration secret sits in a URL: it lands in nginx access logs and browser history, so rotate it after registering.

## Deep Linking and grades (Phase 5 backend)

Rules, all enforced server-side and pinned by `backend/test/integration/lti-grades.test.js`:

- `scenarios.graded` (migration 008) is set at archive upload from the manifest: only `graded: true` makes it true; a
  manifest without the key sets false (also over an earlier graded upload); a non-boolean value is a 400.
- `POST /api/lti/deep-link` (instructor, deep-link session only) answers `text/html`: a form that posts the signed
  `LtiDeepLinkingResponse` JWT to the platform's return URL. One `ltiResourceLink` item: `url` = the tool launch URL,
  `custom.scenario_id` = the catalog id, `lineItem.scoreMaximum` = 100. The response has its own CSP
  (`form-action` and `frame-ancestors` = the platform origin, nonce-only script); nginx leaves `/api/lti/` alone.
- `POST /api/lti/submit` (learner, resource launch only): refuses with 409 `{ error, score }` when Moodle already holds a
  grade for the line item (any source), otherwise posts `{ userId, scoreGiven, scoreMaximum: 100, activityProgress:
  Completed, gradingProgress: FullyGraded }`. A non-graded scenario always reports 1.0; a graded one reports the clamped
  score, 0 when none. A Moodle failure is a 502 and nothing is claimed submitted. Outbound AGS URLs must be https on the
  issuer host, redirects refused.
- Both POSTs reject a foreign `Origin` / non-same-origin `Sec-Fetch-Site` (the session cookie is `SameSite=None`), and
  `submit` accepts `application/json` only.

### Walkthrough findings

- **Fixed: the Deep Linking picker inside Moodle's modal.** Moodle 5 opens "Select content" as a modal *iframe* (no new-window
  option). Two things had to hold in that frame. (1) Framing: `/lti/pick` is the one SPA route served with
  `frame-ancestors` = the Moodle origin(s) from `LTI_FRAME_ANCESTORS` and without `X-Frame-Options`
  (`nginx/nginx.conf`, `location = /lti/pick`; the value is validated at container start by
  `nginx/15-lti-frame-ancestors.sh`, unset means `'self'`); every other page keeps `frame-ancestors 'self'` and
  `SAMEORIGIN`. (2) Cookies: inside the iframe `lti_state_*` and `lti_session` are third-party, so they are set
  `SameSite=None; Secure; HttpOnly; Partitioned` (CHIPS) and keep working with third-party cookies blocked. The
  walkthrough above (2b-2d) ran with Chromium's `--test-third-party-cookie-phaseout` flag. Not exercised: Safari and
  Firefox (their own cookie protections), only Chromium. The resource launch (student, instructor) still uses a
  new window and is unaffected.

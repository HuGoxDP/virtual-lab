# Ручна перевірка у браузері

> **Більшість цього списку тепер автоматизована.** Рендеринг WebGL, втрата
> контексту, повний екран, пастка фокуса, прогрес завантаження і `sendBeacon`
> покриті Playwright-набором у [`e2e/`](../e2e/README.md) — 104 тести:
>
> ```bash
> cd e2e && npm test
> ```
>
> Цей файл лишається для того, що машина або не бачить узагалі, або бачить
> гірше за людину: чи **виглядає** сцена правильно (а не просто чи були
> draw calls), читабельність на реальному телефоні, і поведінка на вашій
> відеокарті замість програмного SwiftShader.

Решта виконується командами `cd backend && npm test` (348 тестів, потрібна тестова БД з
`docker-compose.test.yml`) і `cd frontend && npx ng test --no-watch` (293 тести) і не потребує вашої участі.

**Перед початком:**

```bash
docker compose up -d
cd backend && npm run publish:release   # каталог має бути наповнений
```

Токен для адмінки візьміть з `.env`:

```bash
grep ADMIN_TOKEN .env
```

Позначайте пройдене прямо в цьому файлі.

### 2.1.1 Профайлер вимкнено — <http://localhost:8044/play/solar-system> і `?diag=1`

- [ ] Без прапорця й з `?diag=1`: накладки профайлера (FPS, VRAM, вкладки Stats / Memory) на екрані

- [ ] Клавіша `` ` `` (Backquote) на запущеній сцені нічого не відкриває.
- [ ] З `?diag=1` внизу зліва видно лише мітку збірки рушія (`BuildInfo`) — це єдине, що робить прапорець.

## 5. Стиснені текстури KTX2

Єдиний архів у релізі, який взагалі містить `.ktx2` — це `benchscene3-solarsystem`
(12 текстур). У `solar-system` їх немає, там звичайні PNG/JPEG. Тобто перевіряти
KTX2 можна **тільки** на цій сцені.

Вона `is_published = false`, тому спершу треба тимчасово опублікувати її в `/admin`,
а після перевірки — зняти публікацію.

Файлову половину вже перевірено автоматично (`npm run verify:ktx2` у `backend/`):
усі 12 текстур справді суперстиснені — 11 × ETC1S/BasisLZ і `earth_normal` × UASTC/Zstd.
Тут лишається те, чого не видно з файлів: чи транскодер узагалі завантажився.

- [ ] Відкрити `/play/benchscene3-solarsystem` — текстури планет мають відрендеритись,
      а не бути чорними чи відсутніми.
- [ ] У Network немає 404 на `/assets/basis/basis_transcoder.*`.
      *Двигун за замовчуванням шукає їх у `/basis/`, а Angular публікує під `/assets/` —
      тому `ViewerComponent` передає плеєру `transcoderPath: /assets/basis/`. Без цього
      404 тихий: ані збірка, ані тести його не бачать.*
- [ ] Текстурну VRAM читайте в контексті фрейма плеєра: у DevTools виберіть контекст `player.html`
      зі списку контекстів консолі й виконайте
      `const { MemoryProfiler } = await import(new URL('/assets/WebEngineTS.standalone.js', location.href).href); const r = MemoryProfiler.snapshot().renderer; [r.estimatedTextureVramBytes, r.textureFormats]`
      (`snapshot()` лише читає, нічого не відкриває). Орієнтири для `benchscene3-solarsystem`:

      | Показник | Висновок |
      |---|---|
      | **≈ 36 МБ** | транскодування спрацювало (BC1/BC7) |
      | **≈ 240–280 МБ** | текстури в RGBA8 |

      *Окрім числа VRAM, `r.textureFormats` рахує живі текстури за GPU-форматом
      (наприклад `{ BC7: 3, RGBA8: 1 }`): `RGBA8` для `.ktx2` означає, що транскодування
      не спрацювало. Цифри в таблиці виміряні раніше, до перенесення рушія у фрейм; на новій
      збірці перевірте їх знову.*

> **Станом на 2026-08-13 тут очікувано ≈ 242 МБ, і це не збій платформи.**
> Архів містить і 12 `.ktx2`, і 12 `.jpg`, але `scripts/Scenario.js` завантажує саме
> `.jpg` — тобто `.ktx2` лежать у архіві й ніхто на них не посилається. Транскодер
> при цьому **жодного разу не запитується** по мережі, що це й доводить.
> Виправляти — у `ScenarioCreator`. Перевірено автоматично: `e2e/tests/ktx2.spec.ts`
> (тест сам увімкнеться, коли сценарій почне посилатись на `.ktx2`).

## 5a. Потокова доставка (`?stream=1`) — **потрібна справжня відеокарта**

Сценарій можна віддавати не одним ZIP, а маніфестом окремих файлів. Це вже працює
й покрито автотестами (`e2e/tests/streaming.spec.ts`), але **головне питання
автотести вирішити не можуть**: чи це швидше.

Під SwiftShader розкид між запусками — 30%, більший за сам ефект. Тому цей пункт
має сенс лише на машині зі справжнім GPU.

Спершу наповнити сховище: `cd backend && npm run import:assets`.

- [ ] Відкрити `/play/solar-system?diag=1` (ZIP) і записати мітку збірки рушія (`?diag=1` більше нічого
      не показує: накладки профайлера на платформі немає). Час до першого кадру та текстурну VRAM
      зніміть інструментами рушія (`MemoryProfiler.snapshot()`, харнес `WebEngineTS-Benchmarks`) на
      тій самій збірці, а не з цієї сторінки.
- [ ] Відкрити `/play/solar-system?stream=1&diag=1` (маніфест) і записати те саме.
- [ ] Порівняти. Очікування з наявних вимірів: сцена та сама, але
      **VRAM приблизно втричі більша** на потоковому шляху (269.8 МБ проти 92.8 МБ

      цей шлях студентам за замовчуванням не можна.
- [ ] Кнопка «перезапустити» на потоковому шляху **працює** (новий фрейм і новий запуск із маніфесту),
